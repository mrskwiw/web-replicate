# web-replicate

## Mission — document the app so it can be rebuilt

**Your job is to produce a blueprint complete enough that a developer (or an agent) could reconstruct this application without ever seeing the original.** Not "is it broken?" (that's the sibling `web-qa` skill) — but "how is it built, what does every user path do, and what must the backend provide?" You document two things in reconstruction-grade detail:

- **The frontend, exactly** — for each page and each user path: the rendered markup, the stylesheets and scripts it loads, the asset graph, the interaction surface (every control, form, link), the client state it keeps (Web Storage, cookies), and the console messages it emits.
- **The backend, inferred** — from the traffic those paths generate: which endpoints exist, their methods, request and response *shapes*, the auth scheme, and the data models implied by the payloads. You never see the server's code, so this half is **inference from observation** — labeled as such, with the evidence.

You are the **reasoning half**. A deterministic Python engine under `engine/` is your hands: it drives a real browser and captures structured, sanitized evidence. It makes **no inferences** — turning captures into a backend model and a coherent rebuild spec is entirely your job.

**Think in user paths, not pages.** A page snapshot is a still frame; a *path* is the movie — signup → onboard, create-a-record → edit → export, search → open-result → act. The interesting behavior (which API fires, what state is written, what the response contains) only appears while a real journey runs. Enumerate the journeys a real user takes and record each one end to end.

## Scope & ethics — read before running

- **Only capture systems you own or are explicitly authorized to document.** Replication-grade capture reproduces an app's structure and infers its backend; do this on your own products, a migration you're commissioned for, or a target with written permission. If ownership is unclear, ask the user to confirm before capturing.
- **Passive by default; one narrow active exception.** The capture engine takes *only what normal use loads* — it never fuzzes endpoints, brute-forces routes, or sends requests a user wouldn't trigger. Backend inference reads traffic you generated by using the app, plus state the app already ships to the client (`__NEXT_DATA__`, sourcemaps). Do not hand-craft requests to enumerate a hidden API. **The sole active check is `verify-auth` (§4b):** it re-requests endpoints *you already observed* to confirm their auth — verification, not discovery — is read-only (GET) by default, and is for a target you own. It never touches a route you didn't already surface passively.
- **Secrets are redacted by default.** Captured request/response headers, bodies, and cookie values have auth tokens / credentials / JWTs scrubbed (`«redacted»`). The blueprint documents the *shape* of the contract, not live credentials. `--include-secrets` disables this — use only on your own target when raw values are genuinely required, and treat the output as sensitive.

## Setup (once)

Run from this skill directory (`.claude/skills/web-replicate/`):

```bash
pip install -r requirements.txt && python -m playwright install chromium
```

All engine commands are `python -m engine.cli …` run from here. Each writes its artifacts into a **capture directory** you name (`--out-dir`) and echoes a lean JSON manifest to stdout; large blobs (rendered HTML, response bodies, screenshots) are written to files and referenced by relative path, so what you read stays small while nothing is lost.

## Workflow

### 0. Map the surface & enumerate the user paths

Start with the entry URL. Capture it (step 1) to see the nav, and from the app's own affordances **enumerate the end-to-end journeys a real user takes.** Think in personas and goals, exactly like a QA pass would, but your aim is coverage of *paths*, not correctness:

- The unauthenticated surface: landing → signup/login, marketing/nav routes.
- The core authenticated journeys: onboard, the primary create→read→update→delete loop, any generate/search/export/report action, settings.
- Secondary paths that hit *distinct* endpoints (a different API surface is worth its own trace).

Write the path list down and drive each one in step 2. **Coverage is the deliverable** — a path you never traverse is a backend surface you never observe.

### 1. Capture a page

```bash
python -m engine.cli capture --url <URL> --out-dir capture/<slug> [--screenshot] [--download-assets]
```

Emits a `PageCapture`: `meta` (title/description/viewport/generator/canonical), `tech` (client `frameworks` — prod-build-safe — plus `build_tool`, `libraries`, server/powered-by headers, and a `build_data_ref` to dumped framework state), `interactive` (ranked controls), `forms` (fields + `action`/`method` — a direct backend hint), **`fields`** (see below), `links` (with `scheme`/`external`/`new_tab`), `stylesheets`/`scripts`/`assets`, `inline_styles`, `storage` (local/session/cookies), `console`, and `network`. The **rendered HTML** is saved to `pages/<name>.html` (`html_ref`). Use `capture` for static/entry pages; use `trace` (below) for anything behind an interaction.

- **`fields` — the authoritative control inventory.** Every visible input/select/textarea on the page, each tied to its **resolved visible label** and declared validation (`required`, `minlength`/`maxlength`, `pattern`, `min`/`max`, and `options` for selects). Unlike `forms` (scoped to `<form>` elements), `fields` also captures controls that live **outside any form** — the norm in React/SPA apps that submit via `fetch` — so a multi-step wizard's inputs are documented with their labels instead of anonymous `nth=` selectors. When labels aren't HTML-associated, resolution falls back through wrapping-label → `aria-label` → preceding text → placeholder. (JS-only rules like a Zod schema aren't in the markup, but the label text often encodes them, e.g. "Business Description *0/70 characters".)

- `--download-assets` fetches stylesheet/script/image/font *bytes* into `assets/` — turn it on when you want the actual CSS/JS for byte-faithful replication (off by default; it multiplies capture size and traffic).

### 2. Trace a user path (the core of this skill)

```bash
python -m engine.cli trace --url <ENTRY> --steps <path>.json --out-dir capture/<path> --name "<path name>" [--screenshot]
```

Runs an ordered step list in **one persistent browser context** (state carries across steps — reused from web-qa's `flow`). Each step captures a full `PageCapture` of the after-state **plus the network delta that step generated** — that per-step traffic is your primary backend evidence. A step is an action plus optional keys:

- `type` ∈ `navigate|click|fill|type|press|scroll|wait_for|select`; `selector`, `value`/`text`, `key` as needed.
- `label` (names the step), `intent` (what it accomplishes — carried into the path doc).
- `await_response` (`{method?, path_contains, timeout_ms?}`) — block until that response lands before capturing, for slow async actions (an LLM run, a report build).
- `settle_ms` — extra idle wait for SPA transitions/XHR to land.
- Secrets are referenced by env var: `{"env":"PASSWORD"}` or `${TOKEN}` — **never inline credentials** in the steps file.

The recording (`path.json`) lists each step's action, `url_before`/`url_after`, `http` delta, `console` delta, and a `capture_ref` to that step's full page capture under `steps/`.

**Persistent auth — log in ONCE, then reuse it (inherited from web-qa).** Re-logging-in for every trace burns auth rate limits and trips bot challenges. Run the login path once and save the session; replay it on every later `capture`/`trace`:

```bash
# 1. Establish (ONE login) — credentials from env, UA pinned (tokens are UA+IP-bound).
python -m engine.cli trace --url <BASE>/login --steps login.json \
  --user-agent "Mozilla/5.0 … WebReplicate" --save-session .wr/session.json --out-dir capture/login

# 2. Reuse — every later run starts authenticated.
python -m engine.cli capture --url <BASE>/dashboard --session .wr/session.json --out-dir capture/dashboard
python -m engine.cli trace   --url <BASE>/projects  --session .wr/session.json --steps create-project.json --out-dir capture/create
```

`login.json` is an ordinary steps file (fill email, fill password `{"env":"PASSWORD"}`, click submit, `await_response` the login endpoint). Verify the replay worked: an authenticated page shows logged-in chrome and its network has **no** `/api/auth/login` call.

### 3. Document the frontend (you, from the captures)

Read each capture and write the frontend half of the blueprint. For every page/route:

- **Identity & structure** — route, title, meta, the landmark layout (from `dom_outline`), and the rendered markup in `html_ref` (open it for the exact structure; the outline is just the index).
- **Styling** — the `stylesheets` (URLs; bytes if you used `--download-assets`) and `inline_styles`. Note the CSS approach visible in class names (Tailwind utility classes, CSS modules, styled-components hashes) — it dictates how a rebuild reproduces the look.
- **Interaction surface** — every `interactive` control and the `fields` inventory (label, type, `required`/validation, select `options`) plus `forms` (`action`/`method`, submit). `fields` is the component inventory a rebuild recreates — including formless SPA inputs `forms` can't see.
- **Client state** — the `storage` keys the app writes (localStorage/sessionStorage/cookies) and what they appear to hold. A faithful rebuild reproduces this persistence.
- **Client stack** — `tech.frameworks` (detected even in production builds via DOM instance markers — React fiber keys, Vue's `__vue_app__` — not just globals), `tech.build_tool` (Vite / Next.js / Nuxt / Webpack, inferred from asset URLs), `tech.libraries` (Tailwind, Stripe.js, GA/GTM, Sentry, …), and `evidence` for each call. If `build_data_ref` is set, **read it** (`tech/<name>-build-data.json`) — Next.js `__NEXT_DATA__` / Nuxt / Remix state is often the richest single source of routes, data shapes, and the API base URL. For deeper library detection (e.g. a bundled validator like Zod that exposes no global), capture with `--download-assets` and grep the saved bundles.

### 4. Infer the backend (you, from the traffic — passive)

This is the half no snapshot gives you; it comes from the `network` records across your captures and traces. Assemble a backend model:

- **Endpoint inventory** — every distinct `(method, path)` seen in `xhr`/`fetch`/`document` records across all paths. Group by resource. For each: its purpose (from when it fired and what it returned), whether it required auth, and the **request → response shape** (read `response_body` / the referenced `bodies/*.json`; note the JSON keys and nesting, not the redacted values).
  - **Auth is the one field you cannot read off passive traffic — infer it conservatively.** "The app only called it while logged in" does **not** mean the endpoint *requires* login; public read endpoints (a feed, public like/comment/rating counts) are simply never called logged-out. So mark auth as **inferred** (e.g. `auth: inferred-required (only seen authed)`), never as fact — and **verify it in §4b** to upgrade inferred→verified. Passively over-marking public endpoints as auth-required is the single most common blueprint error.
- **Auth scheme** — how credentials travel: bearer token in `Authorization`, session cookie, CSRF header. Infer from the login response and subsequent request headers.
- **Data models** — the entities the payloads imply (a `Project` with `id`/`name`/`createdAt`, an `Item[]` list shape). Derive field names and types from the response bodies.
- **Base URL / API host** — often in `build_data`, an env-injected config, or simply the common prefix of the API calls. Note if the API is same-origin or a separate host.
- **Framework & infra hints** — `server`/`x-powered-by`/`via` headers, cookie names (e.g. `connect.sid` → Express, `_session` → Rails), and any `/openapi.json` or GraphQL endpoint the app *itself* loaded (read what was captured; do not go fetch new ones — that's active probing).

**Label every backend claim as inferred, and cite the evidence** (which call, which response). Where you're guessing, say so. This honesty is what makes the blueprint trustworthy to rebuild from.

### 4b. Verify the auth column — the one active check (optional, on a target you own)

Passive capture can infer *that* an endpoint carries a cookie, but not *whether the server enforces it* — the gap that makes §4's auth field the least reliable part of the blueprint. `verify-auth` closes it by asking the server directly: it requests each **already-observed** endpoint twice — once with the saved session, once anonymously — and classifies each as `enforced` (anon → 401/403/redirect), `public` (anon → 2xx), or `error-unauth` (anon → 5xx: the guard throws instead of rejecting — a real defect), flagging every result that **contradicts** your inferred auth.

```bash
python -m engine.cli verify-auth \
  --backend ../../../blueprints/<slug>-<date>/backend.json \
  --session .wr/session.json \
  --sub id=<a-real-id-from-an-authed-list-call>
```

- Reads the `endpoints[]` + `base_url` you already rendered (or pass `--base-url`). Endpoints with `{id}`-style params need a real value via `--sub key=value` (grab one from an authed list response); unresolved ones are skipped-and-reported, never guessed.
- **Read-only by default:** only GET is probed. Mutating verbs are withheld and counted (probing a `DELETE`/`POST` would *execute* it) — add `--include-mutating` **only** on a throwaway test target you own.
- **Fold the result back in:** for each endpoint, set `auth_required` to the verified value (e.g. `yes (verified 401)`, `no — PUBLIC (verified)`, or `500 unauthenticated — BUG`) before the final render, and note any `error-unauth` in `backend.notes`. This is what turns the auth column from inference into fact.

This is **verification, not discovery** — it re-asks about endpoints you already surfaced through normal use; it never enumerates or fuzzes hidden routes. (The sibling **web-qa** skill's `sweep` covers the same ground as part of a QA pass; either is a valid way to verify.)

### 5. Assemble & render the blueprint

Build one results object and render it:

```bash
python -m engine.cli blueprint --input results.json --output ../../../blueprints/<site-slug>-<YYYY-MM-DD>
```

**Save every blueprint under the repository-root `blueprints/` directory** (from the skill dir that's `../../../blueprints/`), in a per-run folder `<site-slug>-<YYYY-MM-DD>` (slugify the page title; fall back to the hostname). This writes `blueprint.md` (the human reconstruction spec), `blueprint.json` (full record), and `backend.json` (just the inferred contract, ready to feed a codegen step). Point the capture `--out-dir`s at that same folder so the raw material (`pages/`, `bodies/`, `styles/`, `tech/`, `assets/`, `screenshots/`) lives beside the spec.

`results.json` shape:

```jsonc
{
  "metadata": {"target_url": "...", "engine": "chromium", "captured_at": "2026-07-23", "note": "..."},
  "tech": { /* consolidated TechFingerprint: frameworks, server, evidence */ },
  "backend": {
    "base_url": "https://…/api",
    "auth": "Bearer JWT in Authorization header; issued by POST /api/auth/login",
    "endpoints": [
      {"method": "GET", "path": "/api/projects", "purpose": "list projects", "auth_required": "yes",
       "request_shape": "-", "response_shape": "{ projects: [{id,name,createdAt}] }"}
    ],
    "data_models": [{"name": "Project", "fields": ["id: string", "name: string", "createdAt: ISO8601"]}],
    "notes": ["POST /api/run deducts credits and returns 202 then polls /api/run/{id}"]
  },
  "pages": [ /* the PageCapture manifests (or trimmed summaries) */ ],
  "paths": [ /* the PathRecording manifests */ ]
}
```

Then give the user an in-session summary: which paths were traced, the frontend inventory, the inferred backend surface (with confidence), and any path/route you did **not** cover (so the rebuild scope is honest).

## Safety — destructive actions (mandatory)

**Never fire an irreversible interaction autonomously while tracing** — payments, deletes, sending mail, account changes, or submitting a form that creates a real record. To document such a path, either drive it up to (not through) the irreversible step, or **ask the user for explicit confirmation** before including that step — the session's Claude Code permission settings are the backstop. Read-only/idempotent navigation runs freely. (Same policy as web-qa; there is no engine allowlist — the judgment is yours.)

## Notes & limitations

- **`capture` vs `trace`.** `capture` is one fresh page load (good for entry/static pages). `trace` is the workhorse: a stateful, optionally-authenticated journey where the per-step network deltas are your backend evidence. Prefer `trace` for anything behind a login or an interaction.
- **Backend inference is bounded by what you exercised.** An endpoint no path triggered is invisible. Coverage of *paths* directly determines completeness of the backend model — enumerate journeys deliberately (step 0) and state uncovered surface in the summary.
- **Auth is inferred, then verifiable.** Every auth claim from passive traffic is a guess (§4); `verify-auth` (§4b) upgrades it to fact against a target you own. If you skip verification, keep the auth column marked inferred and say so — don't present inferred auth as verified.
- **Storage: keys kept, secret-shaped values redacted.** localStorage/sessionStorage keys are preserved (a rebuild needs the storage contract), but values under secret-ish keys (`access_token`, `*_token`, `session`, …) or that are JWT/bearer-shaped are redacted — token-in-localStorage auth is common, so the raw token never lands in the blueprint. Non-secret values (e.g. `theme`) are kept. It's a best-effort net; treat any capture as sensitive.
- **`--download-assets`** gets byte-faithful CSS/JS/images but multiplies size and traffic; default off. Turn it on for a final, faithful capture once the path set is settled.
- This skill **documents**; it does not judge whether the app works. For "is this broken / is the output any good?", use the sibling **web-qa** skill.
